# AG6 approval recovery fix

The original missing-artifact failure remains in `report.json`. Approval used to permanently record APPROVED, remove the memory from candidates and approve the request before discovering that no adapter could activate.

The correction reserves a durable ACTIVATING intent, then uses one SQLite transaction for the registry binding, AG6 status/consolidated IDs and request status. AdapterRegistry operates through a transaction-aware store proxy; its ordinary independent transactions and mirror publication are bypassed only inside this manual approval operation. The input hash binds the candidate that the approval reserved. The runner mirror is published atomically while the SQLite write lock is held. Exceptions restore that mirror from the committed registry and reopen PENDING_USER. Interruption before commit leaves the durable intent; construction reconciles the old committed mirror and reopens PENDING_USER without activating the candidate. Failed recovery propagates and preserves the intent. Positive neuromodulation is sent only after successful terminal commit.

SQLite and the filesystem remain separate durability domains. This is a recoverable journaled operation, not a claim of an indivisible filesystem/database transaction. No real deployed weights or user batch were activated during verification.

Sixteen focused real-SQLite/concurrency tests and 52 existing LoRA/growth/neuromod tests pass. The new tests cover missing/tampered artifacts, an activation exception after registry save, restart/retry, normal success, legacy trainers without deployment metadata, request/intent persistence failures, an injected stale-state failure without side-effect retry, competing candidate changes, mirror failure, interrupted publication, failed recovery, previous-binding restoration and an actual COMMIT-time deferred foreign-key failure. `fix-report.json` records before/after/restart observations and file hashes. All fixtures use authored model/adapter bytes; this establishes protocol recovery, not learning quality or Redmi readiness.

## Remaining filesystem reader concurrency limitation

The operator path `:growth approve` currently has no idle requirement or Runtime lock, and `LlamaRunner.load` reads `runner_lora_args` from the filesystem without the Store mutex. A separate thread actually observed candidate arguments after mirror publication but before a subsequent deferred-foreign-key COMMIT failure. After that failure the committed registry/request/consolidation remain unchanged and the old mirror is restored. This does not revoke candidate bytes a native runner could have loaded during that visibility window. No native runner was launched in this authored fixture. `reader-concurrency-report.json` preserves the observation and code hashes. Reader/coordinator serialization remains open; filesystem/database readers are not claimed atomic.

A separate live-intent race is resolved within the owned module: the Store mutex now spans reservation, activation transaction and recovery. A concurrent WeightConsolidation constructor waits for that live operation and observes APPROVED afterward, rather than misclassifying its ACTIVATING intent as an interrupted operation. The exclusive coordinator flock already prevents a second Store owner for the same home.
