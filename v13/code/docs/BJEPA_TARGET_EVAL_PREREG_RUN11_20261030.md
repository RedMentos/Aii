**Technical context (primary code):** Meta's official I-JEPA `facebookresearch/ijepa/src/train.py` and V-JEPA `facebookresearch/jepa/app/vjepa/train.py` use a separate EMA-updated target encoder and `torch.no_grad()` target path. They do not establish that forcing eval mode improves utility for this LLM LoRA variant. Our `BodyJepaTrainer.fit` computes EMA target latents with the shared model still in `train()`; any active dropout may make the same EMA weights produce different targets. This is an uncertainty to isolate, not a reason to rewrite the canonical objective.

**Preregistered candidate:** optional `cfg['jepa_target_eval']=True` (strict bool), default absent/False so all frozen cohorts keep their existing code path and dataset hashes. When explicitly enabled, compute the EMA target under temporary `eval()` and `no_grad()`, with exact restoration of each module's original train/eval flags and student adapter parameters, including on exceptions. The student forward/backward stays in its original training mode; the target remains detached. Add a metric to identify the opt-in mode; no activation in Age0/runtime or model replacement.

**Frozen tiny-torch synthetic tests:** with seeded `torch.manual_seed(13)`, a tiny model with dropout and an EMA adapter must give identical repeated target latents in opt-in eval mode, unlike the original train-mode stochastic control; target `requires_grad=False`, student receives nonzero gradients through predictor/JEPA loss. A child intentionally held in eval must remain in eval after temporary target pass, and an injected forward exception must restore adapter bytes and all module flags. Existing `test_body_jepa` and checkpoint tests must still pass. This is an opt-in research candidate; no claim that it improves generalization, STEP2, JEPA weight or phone utility.
